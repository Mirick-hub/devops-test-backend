Під час виконання **можна і потрібно** користуватися:

- Google;

- будь-якими іншими навчальними матеріалами.

# Частина 1. Python Backend

## Вхідні дані

Вам буде надано готовий невеликий Python backend-проєкт із:

- кількома існуючими API endpoint’ами;
- моделями та базою даних;
- базовою структурою проєкту;
- готовим способом локального запуску.

Перед внесенням змін потрібно самостійно розібратися:

- який framework використовується;
- де описані endpoint’и;
- де знаходяться моделі;
- як застосунок працює з базою даних;
- як запустити проєкт локально;
- як перевіряти API.

---

## Завдання 1. Додати фільтрацію до існуючого endpoint

В одному з існуючих endpoint’ів зі списком сутностей потрібно реалізувати фільтрацію через query parameters.

Наприклад, якщо API працює із задачами, товарами, користувачами або замовленнями, клієнт повинен мати можливість отримувати лише записи, що відповідають заданим параметрам.

### Очікується

- існуючий endpoint продовжує працювати без параметрів;
- можна передати один або кілька параметрів фільтрації;
- фільтри реально впливають на результат;
- некоректні параметри не повинні призводити до `500 Internal Server Error`;
- рішення не повинно дублювати зайву логіку.

---

## Завдання 2. Створити новий endpoint

Потрібно додати один новий API endpoint, який повертає корисну інформацію на основі даних, що вже є в системі.

Приклади того, що це може бути:

- статистика;
- агреговані дані;
- детальна інформація про одну сутність;
- список пов’язаних об’єктів;
- окрема бізнес-операція.

Конкретну реалізацію потрібно спроєктувати самостійно, орієнтуючись на структуру наданого проєкту.

### Очікується

- endpoint має зрозумілий URL та HTTP method;
- повертається коректний HTTP status code;
- відповідь має зрозумілу JSON-структуру;
- коректно обробляються ситуації, коли потрібних даних немає;
- реалізація відповідає підходам, які вже використовуються в проєкті.

---

## Завдання 3. Додати нову функціональність

Потрібно реалізувати невелику бізнес-функцію поверх існуючих моделей.

Приклади:

- зміна статусу об’єкта;
- перевірка доступності перед виконанням операції;
- автоматичне оновлення пов’язаного поля;
- створення пов’язаного запису;
- валідація певного бізнес-правила.

Приклад бізнес-правила:

> Неможливо виконати операцію, якщо об’єкт уже знаходиться у фінальному статусі.

Або:

> Після створення операції потрібно автоматично оновити значення пов’язаного об’єкта.

Конкретний спосіб реалізації потрібно визначити самостійно.

### Очікується

- бізнес-правило реально працює;
- враховані основні edge cases;
- API не падає на очікуваних помилкових сценаріях;
- клієнт отримує зрозумілу відповідь про помилку;
- нова функціональність не ламає існуючу.

---

## Перевірка Backend-частини

Після завершення потрібно продемонструвати:

- локальний запуск застосунку;
- роботу зміненого endpoint із фільтрами;
- роботу нового endpoint;
- роботу доданої бізнес-функції;
- приклади успішних та помилкових запитів.

Для перевірки API можна використовувати будь-який зручний інструмент, наприклад:

- Swagger / OpenAPI UI;
- Postman;
- Insomnia;
- `curl`;
- браузер, якщо endpoint підтримує GET.

# Частина 2. DevOps

## Мета

Потрібно взяти готовий backend-проєкт та пройти базовий шлях доставки застосунку:

**локальний код → Git → віддалений repository → автоматична перевірка → deployment → застосунок в інтернеті**

Точний спосіб реалізації потрібно знайти та обрати самостійно.

---

## Завдання 1. Додати Git

Проєкт потрібно перевести під контроль версій.

### Очікується

- створений Git repository;
- файли проєкту додані до repository;
- створений початковий commit;
- службові та локальні файли не потрапляють у Git;
- історія змін залишається зрозумілою.

---

## Завдання 2. Завантажити проєкт у віддалений repository

Потрібно створити remote repository та завантажити туди код.

Можливий інструмент:

- **GitHub**

Також можна використати інший Git hosting.

### Очікується

- код доступний у remote repository;
- основна гілка містить актуальну версію проєкту;
- секрети та локальні конфігурації не зберігаються відкрито в repository.

---

## Завдання 3. Контейнеризувати застосунок

Потрібно зробити так, щоб backend можна було запускати в контейнері.

Можливий інструмент:

- **Docker**

### Очікується

- у repository є конфігурація для створення container image;
- image успішно збирається;
- container запускається;
- API доступне з локальної машини;
- необхідні порти налаштовані коректно;
- конфігурація застосунку не повинна жорстко залежати від конкретного комп’ютера.

---

## Завдання 4. Налаштувати CI

Після кожного push або pull request система повинна автоматично перевіряти проєкт.

Можливий інструмент:

- **GitHub Actions**

Можна використати іншу CI-систему.

### Мінімальна перевірка

Pipeline повинен виконувати хоча б частину з наступного:

- встановлення dependencies;
- запуск тестів;
- перевірку, що застосунок збирається;
- lint / formatting checks;
- побудову Docker image.

### Очікується

- pipeline запускається автоматично;
- успішний код дає успішний pipeline;
- навмисно зламана перевірка повинна зробити pipeline failed;
- у логах CI можна зрозуміти причину помилки.

---

## Завдання 5. Deploy застосунку

Потрібно розгорнути backend на віддаленому hosting-середовищі так, щоб API можна було відкрити через публічний URL.

Можливі інструменти:

- **Render**
- **Koyeb**
- інший безкоштовний або trial hosting

Спосіб deployment потрібно знайти самостійно.

### Очікується

- застосунок доступний через публічний URL;
- API реально відповідає на запити;
- після deployment можна перевірити хоча б health endpoint або інший простий endpoint;
- конфігурація production-середовища не зберігається прямо в коді.

---

## Завдання 6. Налаштувати CD

Потрібно автоматизувати deployment нової версії.

Очікуваний flow:

```text
Push у main
    ↓
CI
    ↓
Перевірки успішні
    ↓
Deploy
    ↓
Нова версія доступна в інтернеті
```

### Очікується

- deployment не виконується, якщо CI завершився з помилкою;
- після успішної перевірки запускається deployment;
- зміна, відправлена в основну гілку, може дійти до віддаленого середовища без ручного копіювання файлів.

---

## Завдання 7. Environment Variables та Secrets

Потрібно визначити, які параметри застосунку не повинні зберігатися безпосередньо в коді.

Наприклад:

- database connection string;
- secret key;
- API token;
- deployment hook;
- інші credentials.

### Очікується

- секрети не потрапляють у Git;
- локальна та віддалена конфігурація можуть відрізнятися;
- необхідні значення передаються через environment variables або secret storage відповідної платформи.

---

## Завдання 8. Troubleshooting

Після завершення deployment потрібно вміти знайти причину проблеми, якщо застосунок перестає запускатися або відповідати.

Потрібно розібратися:

- де дивитися application logs;
- де дивитися CI/CD logs;
- як перевірити, чи завершився deployment успішно;
- як знайти проблему з environment variables;
- як перевірити, чи запускається container;
- як зрозуміти, на якому етапі сталася помилка.

# Фінальний результат

Після виконання всього завдання очікується:

### Backend

- змінений існуючий endpoint із фільтрацією;
- один новий endpoint;
- одна нова бізнес-функція;
- коректна обробка типових помилок;
- працездатний локальний застосунок.

### DevOps

- Git repository;
- remote repository;
- Docker-конфігурація;
- автоматичний CI pipeline;
- публічно доступний deployment;
- автоматизований або напівавтоматизований CD flow;
- конфігурація через environment variables / secrets;
- розуміння, де шукати logs та як розбирати проблеми.
